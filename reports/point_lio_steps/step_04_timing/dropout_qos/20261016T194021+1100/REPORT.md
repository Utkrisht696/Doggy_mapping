# Dropout/QoS comparison — 16 October 2026

Status: **Comparison complete; real host UDP receive-buffer overflows identified.**
No adapter code, active configuration, timestamps, TF, OS settings or robot settings
were changed. The user requested one-at-a-time diagnosis and confirmation before
code/config changes. Calibration and mapper work have not advanced.

Five independent single-threaded observer processes ran simultaneously for each
phase: source best-effort depth 5, source best-effort depth 2000, two independent
source reliable depth 2000, and reliable calibrated-output depth 10000. Each observer
saved source stamp, host time, monotonic callback time and IMU fields. The independent
processes avoid a shared executor starving one subscription because of another.
The actual adapter remained unchanged and running. Both phases use the same set of
observers. The second adds the ten-topic rosbag workload. No synthetic CPU load or
robot movement was requested. The observers/recorder are stopped now.

Use the common SOURCE-time interval after one-second boundary exclusions. For each
phase, compare unique source timestamps to the union observed by the four source
observers. This is an observed reference, not all physical samples generated by
the robot. Multiple messages with one identical source stamp are deduplicated.

The output-capture row includes any loss at the adapter or output observer; it is
not an exact count of adapter callback drops. Some calibrated-output stamps were
not observed by any source observer, which also demonstrates the union is incomplete.
Per-socket counters cover all DDS datagrams received on that socket, not only the
SportModeState topic. Host-global counters include other UDP applications. Nonetheless
the existing IMU adapter's own socket drop counter increased during each run, giving
direct evidence of laptop-side receive loss. Ethernet counters show no link-level
RX error/drop increases in these runs; this does not prove the entire network loss-free.

Current kernel rmem_max and rmem_default are 212,992 bytes. ss reports the adapter's
actual socket rb=425,984 bytes (Linux accounting includes doubling) and increasing
drop counter. CycloneDDS can request a larger buffer but is constrained by the
kernel cap. Primary-source guidance describes this issue and recommends raising
receive buffer limits for large ROS samples:
https://github.com/ros2/rmw_cyclonedds/blob/humble/README.md
https://cyclonedds.io/content/faq.html
The 0.10-series configuration schema supports SocketReceiveBufferSize min/max:
https://github.com/eclipse-cyclonedds/cyclonedds/blob/releases/0.10.x/etc/cyclonedds.xsd

Queue-depth/reliability changes help observed completeness under load but are not
a complete socket-overflow fix. Under recording load, p99 callback delay relative
to the earliest SOURCE observer was 11.72 ms for BE5, 150.45 ms for BE2000 and
140.35 ms for reliable2000; corresponding maxima were 41.04, 226.36 and 257.66 ms.
This measures relative observer callback delay, not sensor acquisition lag or
network one-way latency. Reliable delivery and deeper queues can retain delayed
samples, so neither should be selected based only on the missing-message count.
The live adapter output had median +2.64 ms relative callback delay, but a negative
minimum because the actual adapter can receive a packet before all audit sources.

All matched source/output acceleration/gyro values preserve the approved bias math
exactly; all observed stamp sequences have no backward steps. Three >12 ms gaps
per phase are common to the source-observer union. These may involve publishing,
shared transport or stamp generation; there is no proof of a physical sampling gap.
